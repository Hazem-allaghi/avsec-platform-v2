# Supabase Auth Integration — الحالة الفعلية والحدود

## ما تم بناؤه واختباره فعليًا (في هذه البيئة، بلا شبكة خارجية)
| المكوّن | الملف | الحالة |
|---|---|---|
| مخطط Postgres + RLS كامل | `supabase/migrations/0001_init.sql` | مكتوب، **غير مُنفَّذ على مشروع حي** (لا اتصال شبكة هنا) |
| جدول `profiles` مرتبط بـ `auth.users` | نفس الملف | مكتوب، يتبع نمط Supabase القياسي |
| تحقق JWT (توقيع، صلاحية، انتهاء) | `backend/app/auth.py` | ✅ **مُختبَر فعليًا** — `verify_jwt()` يرفض توكنات منتهية، يرفض تواقيع خاطئة، يقبل توكنات صحيحة |
| Decorator صلاحيات (`require_auth`) | نفس الملف | ✅ **مُختبَر فعليًا** على 7+ نقاط نهاية حرجة |
| فرض شرط الصورة لـ BR-06 (قرار #3) | `backend/app/main.py::create_override` | ✅ **مُختبَر فعليًا** (400 بلا صورة، 201 معها) |
| توليد توكن تجريبي محاكٍ لتوكن Supabase | `backend/app/dev_tokens.py` | أداة تطوير/اختبار فقط — **لا تُستخدم في الإنتاج إطلاقًا** |

**دليل الاختبار الفعلي:** `tests/e2e_auth_smoke_test.py` — يغطي 401 (بلا توكن)،
401 (توكن منتهي)، 403 (دور خاطئ لنقطة النهاية)، 403 (دور خاطئ لقاعدة تجاوز
محددة)، 400 (تجاوز BR-06 بلا صورة)، 201/200 (المسارات الصحيحة الكاملة)،
وتسلسل فتح/رفض إغلاق/قبول إغلاق لحالة طوارئ حسب الدور.

## ⚠️ ما لا يمكن اختباره من هذه البيئة تحديدًا
بيئة التنفيذ هذه (Sandbox) **بلا اتصال إنترنت خارجي** (network egress
معطَّل بالكامل). هذا يمنع فعليًا:
1. الاتصال بمشروع Supabase حقيقي على supabase.com.
2. تنفيذ `supabase db push` أو تشغيل `0001_init.sql` على قاعدة Postgres حية.
3. إصدار توكن حقيقي عبر Supabase Auth API (تسجيل دخول فعلي، Magic Link، إلخ).
4. تثبيت `psycopg2`/`psycopg` (غير مُثبَّتين في هذه البيئة ولا يمكن تنزيلهما
   بلا شبكة) — لذلك الـ Backend الحالي **لا يزال يعمل فعليًا على SQLite
   محليًا**، مع أن كل منطق التحقق من JWT والأدوار مطابق تمامًا لما سيُستخدم
   مع Postgres/Supabase (نفس `backend/app/auth.py` بالضبط).

## ما تحتاجه مني لإكمال الربط الحي (بالترتيب)
1. **إنشاء مشروع Supabase** (إن لم يكن موجودًا) على supabase.com.
2. تزويدي بـ 4 قيم بيئة (Environment Variables) — **لا تُرسلها هنا كنص
   عادي في المحادثة لأسباب أمنية، ضعها مباشرة في `.env` على خادمك أو أرسلها
   عبر قناة آمنة:**
   - `SUPABASE_URL`
   - `SUPABASE_ANON_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `SUPABASE_JWT_SECRET` (هذا فقط ما يستخدمه `auth.py` فعليًا للتحقق محليًا
     من التوقيع — الثلاثة الأخرى تلزم للاتصال بـ REST/Admin API لاحقًا)
3. تشغيل الترحيل الفعلي: `supabase db push` (من جهازك/خادمك، ببيئة لديها
   اتصال إنترنت) لتطبيق `supabase/migrations/0001_init.sql`.
4. إدخال بيانات `profiles` الأولية (CSO، Supervisors، Officers…) — إما يدويًا
   من Supabase Dashboard، أو عبر سكربت أُجهّزه لك بمجرد تأكيد بنية الحسابات
   الفعلية لموظفي AAW.
5. بعدها فقط: تبديل الـ Backend من SQLite إلى الاتصال الفعلي بـ Postgres عبر
   `psycopg2` (يحتاج تثبيت الحزمة — ممكن في بيئتك، غير ممكن هنا).

## القرار الهندسي الذي يُبقي هذا آمنًا رغم القيد الحالي
لم أُخمّن أو أُحاكِ استجابة Supabase وهميًا لأدّعي نجاحًا غير حقيقي. الكود
الحالي **إما يعمل فعليًا (SQLite + JWT حقيقي التحقق)، أو يبقى معلَّقًا بوضوح
(Postgres/RLS الحي) بانتظار بيانات اعتماد حقيقية منك.** لا شيء مُقدَّم هنا
على أنه "مُختبَر" وهو ليس كذلك.
